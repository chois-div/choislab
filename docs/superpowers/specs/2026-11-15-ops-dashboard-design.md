# 초이스랩 운영 대시보드 (`/ops/`) 설계

## 배경

choislab 레포에는 이미 3개의 흩어진 운영 도구가 있다.

1. `/admin/` — Sveltia CMS. `data/portfolio.json`을 편집하는 포트폴리오 관리 화면. GitHub 로그인으로 보호됨. 이미 라이브.
2. `/quote/` — 비밀번호(SHA-256 해시 비교, 메모리에만 보관)로 보호된 견적서 목록/작성 도구. Google Apps Script를 백엔드로 사용. 이미 라이브.
3. `contract-docket/` — 전자계약(서명) MVP. Next.js 풀스택 앱. 이 스펙 작성 도중 별도 세션에서 Supabase 이메일 매직링크 인증(접근 허용 이메일 목록 기반) + Supabase DB·Storage 영속 저장소가 이미 추가됨(코드 레벨로는 준비됨). 다만 **Supabase 프로젝트 실제 생성, 호스팅(Vercel 등) 배포, SMTP·환경변수 설정은 아직 안 되어 있어 어디에도 라이브로 떠있지 않음.**

이 세 도구를 매번 따로 들어가서 확인해야 하는 번거로움을 줄이기 위해, 하나의 진입점에서 핵심 지표를 요약해서 보여주는 대시보드가 필요하다.

추가로, 사용자가 관리하는 아임웹(Imweb) 고객 사이트 3개 이상에서 들어오는 문의(아임웹 기본 "입력폼" 기능 사용)도 같은 대시보드에서 사이트별로 확인하고 싶다는 요구가 있었다.

## 범위

**이번 스펙에 포함:**
- `/ops/index.html` 통합 대시보드 (포트폴리오 / 견적서 / 아임웹 문의 / 계약-준비중 카드 4개)
- 기존 `/quote/` 비밀번호를 그대로 재사용하는 단일 로그인
- 아임웹 문의 건수를 안전하게 가져오기 위한 작은 백엔드(`ops-api`, Render 무료 티어, SEO 분석기와 동일한 배포 패턴)

**이번 스펙에서 제외 (별도 후속 프로젝트로 분리):**
- contract-docket의 실제 배포 — 인증(Supabase 매직링크)과 영속 저장소(Supabase DB/Storage)는 코드상 이미 준비돼 있지만, Supabase 프로젝트 생성·호스팅 배포·SMTP 설정 등 실제로 띄우는 작업이 아직 하나도 안 됐다. 이 설정 작업은 계정 가입이 필요해 사용자가 직접 해야 하는 단계가 많으므로 별도 스펙으로 분리한다. 대시보드에는 일단 "준비 중" 플레이스홀더 카드만 둔다.
- 아임웹 방문자/트래픽 통계 — 아임웹 공식 Open API에 해당 엔드포인트가 없어 애초에 불가능함을 조사로 확인했다.
- `/admin/`(GitHub 로그인)을 포함한 완전한 SSO 통합 — admin 진입 시 기존 GitHub 로그인은 그대로 유지한다.

## 아키텍처

정적 사이트(GitHub Pages)에 페이지 하나를 추가하는 기존 패턴(`/admin/`, `/quote/`와 동일)을 따른다. 새 서버 프레임워크나 빌드 도구는 들이지 않는다.

```
choislab (GitHub Pages, 정적)
├── /ops/index.html        ← 신규. 비밀번호 게이트 + 대시보드
├── /admin/                ← 기존 그대로 (Sveltia CMS, GitHub 로그인)
├── /quote/                ← 기존 그대로 (비밀번호, Apps Script)
└── data/portfolio.json    ← 기존 그대로 (포트폴리오 데이터 원본)

ops-api (Render, 무료 티어, 신규)
└── 사이트별 {이름, 아임웹 API Key, Secret}을 환경변수로 보관
    GET /api/inquiries  →  사이트별 최근 7일 신규 문의 건수 반환
```

`/ops/`는 `robots.txt`에 noindex 처리하고, 공개 네비게이션·sitemap·llms.txt에는 올리지 않는다 (`/admin/`과 동일한 보안 수준).

왜 아임웹 문의 조회만 백엔드가 필요한가: 아임웹 Open API는 사이트별 `API Key + Secret`을 `GET api.imweb.me/v2/auth`에 넘겨 토큰을 받는 방식이다. Secret을 브라우저(정적 페이지의 JS)에 그대로 두면 누구나 개발자 도구로 훔쳐볼 수 있으므로, Secret은 반드시 서버에만 둬야 한다. 포트폴리오(공개 JSON)와 견적서(이미 존재하는 Apps Script, 자체적으로 키 기반 접근 제어)는 이런 문제가 없어 그대로 클라이언트에서 직접 호출한다.

## 화면 구성

### 1. 비밀번호 게이트
`/quote/index.html`과 동일한 방식을 그대로 재사용한다. 비밀번호의 정답은 로컬에 저장돼 있지 않다 — 입력값을 SHA-256으로 변환한 값(KEY)을 기존 Google Apps Script 엔드포인트의 `action=ping`에 `key` 파라미터로 보내면, Apps Script가 서버에 저장된 진짜 해시와 비교해 `{ok:true, rows:N}` 또는 `{ok:false, error:'인증 실패'}`를 돌려준다. 이 응답으로 통과 여부를 판단한다. KEY는 통과 후 메모리 변수에만 보관하고 어디에도 저장하지 않는다. 새 비밀번호를 만들지 않고, 비밀번호의 진짜 값은 여전히 Apps Script 쪽에만 있다 (단일 진실 공급원 유지).

### 2. 대시보드 (비밀번호 통과 후)

4개 카드를 보여준다.

| 카드 | 표시 내용 | 데이터 출처 | 클릭 시 이동 |
|---|---|---|---|
| 포트폴리오 | "포트폴리오 N건" | `data/portfolio.json` 직접 fetch (인증 불필요) | `/admin/` |
| 견적서 | "견적서 N건" + 가장 최근 건 이름 | 기존 Apps Script `action=list&key=<KEY>` | `/quote/` |
| 아임웹 문의 | 사이트별로 "OO사이트 N건(최근 7일)" 목록 | `ops-api`의 `GET /api/inquiries` | (고객 사이트별 아임웹 관리자 URL, 설정값으로 보유) |
| 계약(전자계약) | "준비 중" 고정 텍스트 | 없음 (정적) | 없음 (비활성 카드) |

## 데이터 흐름

1. 페이지 로드 → 비밀번호 입력창
2. 입력값 SHA-256 변환(KEY) → `<Apps Script 엔드포인트>?action=ping&key=<KEY>` 호출
3. 응답이 `{ok:true}`면 통과 → 대시보드 노출, KEY를 메모리 변수에 보관. `{ok:false}`면 "비밀번호가 맞지 않습니다" 인라인 에러
4. 다음 두 요청을 병렬로 실행:
   - `GET /data/portfolio.json` (same-origin, 인증 없음)
   - `GET <Apps Script 엔드포인트>?action=list&key=<KEY>`
5. `GET <ops-api 주소>/api/inquiries` 호출 시 3단계에서 만든 KEY를 `X-Ops-Key` 헤더로 함께 전달. `ops-api`는 그 KEY를 그대로 들고 같은 Apps Script의 `action=ping`을 서버사이드로 한 번 호출해 `{ok:true}`인지 확인한 뒤에만 아임웹 조회를 진행한다 (비밀번호의 진짜 값은 Apps Script에만 있으므로, ops-api도 별도로 비밀번호를 저장하지 않고 같은 곳에 물어봐서 검증 — "하나의 비밀번호로 통일" 요구사항 그대로 유지)
   - `ops-api`는 내부적으로 설정된 사이트 목록을 순회하며:
     a. 각 사이트의 Key/Secret으로 아임웹 `v2/auth` 호출 → access_token 발급
     b. 발급된 토큰으로 "입력폼 제출 목록 조회" 호출
     c. 응답에서 최근 7일 이내 제출 건수만 집계
   - 사이트별 결과를 배열로 모아 한 번에 응답
6. 계약 카드는 네트워크 요청 없이 즉시 "준비 중"으로 렌더링

## 에러 처리

- 비밀번호 불일치 → 대시보드 노출하지 않고 인라인 에러 메시지 (`/quote/`와 동일한 UX)
- 포트폴리오 JSON 로드 실패 → 해당 카드만 "불러오기 실패", 나머지 카드는 영향 없음
- 견적서 Apps Script 호출 실패/타임아웃 → 해당 카드만 "불러오기 실패"
- 아임웹 문의 조회 중 특정 사이트 1곳이 실패(토큰 발급 실패, 타임아웃 등) → 그 사이트 행만 "조회 실패" 표시, 나머지 사이트는 정상 표시. 한 사이트의 장애가 전체 카드를 막지 않는다.
- `ops-api` 자체가 다운됨 → 아임웹 문의 카드만 "불러오기 실패", 포트폴리오/견적서/계약 카드는 영향 없음 (완전히 독립된 호출이므로)

## 구현 전 준비 사항 (사용자가 직접 할 일)

- 각 고객 아임웹 사이트 관리자 페이지 → 환경설정 → 외부 서비스 연동(API)에서 API Key/Secret 발급
- 발급받은 Key/Secret과 사이트 이름 목록을 전달 → `ops-api`의 Render 환경변수로 등록

## 테스트 방법

브라우저로 직접 확인한다 (별도 자동화 테스트는 이번 범위에서 만들지 않는다):
- 틀린 비밀번호 입력 시 대시보드가 열리지 않는지
- 올바른 비밀번호로 대시보드가 열리는지
- 포트폴리오 건수가 `data/portfolio.json`의 실제 항목 수와 일치하는지
- 견적서 건수가 `/quote/`에서 보이는 목록과 일치하는지
- 아임웹 문의 카드가 설정된 사이트 수만큼 줄이 나오고, 각 건수가 각 사이트 아임웹 관리자에서 보이는 최근 문의 건수와 대략 일치하는지
- 사이트 1곳의 Key/Secret을 의도적으로 잘못 설정했을 때 그 행만 실패 표시되고 나머지는 정상인지
- `/ops/`가 검색엔진에 노출되지 않는지 (`robots.txt`, `noindex` 메타 태그 확인)

## 후속 프로젝트 (이번 범위 아님)

- contract-docket 실배포: Supabase 프로젝트 생성, 호스팅(Vercel 등) 결정, SMTP 설정, 환경변수 등록 — 인증·저장소는 코드상 준비됐으니 "배포" 자체가 남은 일. 별도 스펙으로 진행
- 대시보드 비주얼 디자인을 Figma로 시안화 (Figma 연동 재인증 필요, 사용자 요청으로 대기 중)
